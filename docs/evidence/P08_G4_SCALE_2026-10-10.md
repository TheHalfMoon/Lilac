# P08-G4: large projects, measured, with proposed budgets

Issue: #230 (P08 umbrella), founder section P08.4: large projects with measured budgets.

**Status: measured. The budgets below are proposals for the founder to accept at the P08 exit gate; none is accepted yet.**

P06 set package-level budgets for the document model, history and persistence at 10,000 and 50,000 layers (`docs/evidence/P06_G3_PERFORMANCE_BUDGETS_2026-10-07.md`). This grain measures the integrated product instead: through the studio host's HTTP API and its MCP endpoint, as the editor and an agent use it.

## What runs
- **`tests/support/scale.mjs`** holds the workloads. `node tests/support/scale.mjs [sizes]` prints a report; the default sizes are 1,000, 10,000, 25,000 and 50,000 layers.
- **`tests/scale-report.test.mjs`** runs them at CI size on every CI run and prints the numbers. Its only checks are ceilings at about ten times what was measured, so a collapse fails while a slower runner does not.

**The workloads:**
- **Flat projects:** pages of 50 cards, each a frame with a text, built with edits of up to 5,000 operations. On each:
  - 30 one-change edits, 10 undos, 10 redos;
  - reading the document;
  - exporting a page as code;
  - an agent reading a layer and making 10 text edits through MCP;
  - a checkpoint, a close (with its checkpoint, #243), and a reopen in a new host.
- **A tree 1,000 levels deep** (the limit is 1,024): an edit at the bottom, a close, a reopen.
- **A long history:** a host in its own process makes one-change edits and is killed, and the project is reopened, replaying them.
- **An HTML import** at 80% of the 10,000-node import limit: review, then commit.
- **A codebase write-back** on a component at the size code import accepts: scan, bring in, preview, write.

## Measurements
**Platform:** Windows 11, Intel Core i5-13420H (12 threads), Node 24.19. CI runs Node 22, so its log's figures are on another runtime as well as other hardware.
- **Sampling:** each figure comes from one run. For repeated operations it is the p50 / p95 of their samples. "p95" is the nearest-rank 95th percentile: with 10 samples (undo, redo, an agent's edit, the deep edit) or 15 (the CI run's 10,000-layer edit) it is the largest sample, and with 30 (edits) the second largest.
- **Save time:** an edit is the save. Every committed edit is written and synced to the journal before the host answers, so edit latency includes the durable write. A close adds the checkpoint (#243).
- **Commands:** every figure below comes from one run of `node tests/support/scale.mjs` (the full sizes, with both crash histories) at this PR's head. An earlier run, before the 10,000-layer history was part of the script, gave the same picture within a few percent (24.9 s for that recovery).

## What the measurements show
- **An edit's cost grows with the whole document, at about 20–26 µs per layer:** #252.
  - Every commit validates and clones the whole document, whatever the edit touches.
  - At 1,000 layers editing feels immediate. At 10,000 it takes about a fifth of a second. Beyond 25,000, each change takes more than half a second.
  - An agent's edit costs about 20–30% more, for the MCP call and its authorization.
- **Recovery after a crash replayed each entry against the whole document:** #251, now fixed.
  - At 10,000 layers each replayed entry cost about 83 ms. A 2,000-edit session would have taken close to three minutes to come back.
  - The fix replays the pending entries on one copy of the document and validates the result once. Measured again with `tests/support/scale.mjs` on the same machine after the fix: 302 entries on 10,000 layers in 0.43 s, 1,002 entries on 10,000 layers in 0.56 s, and 2,001 entries on 1,000 layers in 0.15 s.
  - Since #243, a clean close checkpoints, so replay happens only after a crash.
- **Bringing in a component from code stops at about 10 KiB of JSX:** #250. That is 256 list items, or 510 elements of a card page (found by bisecting component sizes against `importJsx`, as recorded in #250), while the codebase scan reads files of up to 256 KiB.
- **Opening, closing, reading, exporting, importing and writing back are fast enough at every size measured:**
  - reopening 50,000 layers after a clean close takes 1.6 s;
  - closing takes 0.24 s;
  - an 8,000-layer HTML import takes 1.1 s;
  - a write-back takes under 0.1 s.
- **Disk:** the journal holds about 160 bytes per layer built. The object store holds about twice the document, because a checkpoint and the close each write one. Unreferenced objects are never removed (#244).

## Proposed budgets (for founder acceptance at the P08 exit gate)
The measured behaviour sets the proposals, together with what keeps the product usable: about 100 ms feels immediate, and about 300 ms is acceptable for a discrete action.

| Budget | Proposed | Measured now | Meets it |
|---|---|---|---|
| Supported size | Comfortable up to 10,000 layers; supported, with slower edits, up to 50,000; the hard limit stays 100,000 | — | — |
| Edit, undo, redo at 1,000 layers | p95 ≤ 100 ms | 44, 41, 36 ms | yes |
| Edit, undo, redo at 10,000 layers (on the reference machine above) | p95 ≤ 300 ms now; ≤ 100 ms after #252 | 214, 192, 207 ms | now yes; target no |
| Agent edit at 10,000 layers | p95 ≤ 400 ms | 262 ms | yes |
| Reopen after a clean close | ≤ 1 s at 10,000; ≤ 3 s at 50,000 | 0.25 s; 1.65 s | yes |
| Close | ≤ 0.5 s at 50,000 | 0.24 s | yes |
| Recovery after a crash | ≤ 5 s for 1,000 replayed entries at 10,000 layers | 1,002 entries in 0.56 s since the #251 fix (before it, 302 entries took 25.2 s) | yes, since the #251 fix |
| HTML import | ≤ 3 s at the 10,000-node import limit | 1.1 s at 8,000 (review 0.53 s, commit 0.57 s) | yes |
| Write-back | preview and write ≤ 0.5 s at the code import limit | 83 ms | yes |
| Code import | a component up to the 256 KiB the scan accepts | about 10 KiB | **no: #250** |
| Memory | ≤ 500 MiB growth at 50,000 layers (indicative, see above) | 180 MiB | yes |
| Disk | the object store bounded by a few snapshots of the document | it grows each editing session | **no: #244** |
