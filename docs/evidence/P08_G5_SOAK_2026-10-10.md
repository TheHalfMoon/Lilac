# P08-G5: soak

Issue: #230 (P08 umbrella), founder section P08.5: drift, leaks (memory, handles, child processes, temporary files), journal growth, nondeterminism and degradation.

**Status: measured. One degradation found and filed (#258); the object store's growth (#244) is quantified. Child processes are not exercised by this soak (see the last section).**

## What runs
- **`tests/support/soak.mjs`** drives one long session through the studio host. `node tests/support/soak.mjs [rounds] [seed]` prints a JSON report.
- **`tests/soak.test.mjs`** runs 600 rounds on every CI run, twice with the same seed (about 37 s here). `NINERR_SOAK_ROUNDS` sets the rounds.

**What the CI test checks:**
- **Tripwires** for a gross regression in latency, the heap after a full collection, and open resources. At 600 rounds they cannot show slow drift. Only a jump of about 35 times the drift found below, or a leak of 40 KiB or more per round, would fail them; the long run is what shows drift.
- **After the hosts close:**
  - nothing is left running;
  - the project folder holds only the project's own files and folders;
  - the codebase holds only its own file.
- **Same seed, same result:** both runs end in the same document, with the same layers, journal and object store at every window.

**Each round is one action, drawn from the seed:**

| Action | Share |
|---|---:|
| The person's edit: add a layer, change one or remove one | 45% |
| An agent's edit through MCP | 10% |
| Undo | 8% |
| Redo | 6% |
| Reading the document | 10% |
| Exporting a page as code | 5% |
| An HTML import, committed then removed | 4% |
| A write-back to a connected codebase (edit, preview, write) | 5% |
| A checkpoint | 6% |
| Closing and reopening the project in a new host | 1% |

**At a reopen:**
- the project must come back with the same document and revision;
- the editor's live event stream, which the soak keeps open throughout, must end with its host.

**The session stays the same size.** Layers are added and removed in balance, and every import removes all imported pages, since an undo can bring one back. A change in latency is therefore the host's, not a larger document's (#252). The table's "Layers" counts every node in the document.

Every 500 rounds the soak records:
- the median of the person's edit latency;
- the heap after a full collection, and the resident memory;
- the journal and object store size on disk;
- the number of the process's active resources (sockets, servers, child processes and referenced timers).

**The process holds both the host and the code that drives it** (HTTP and MCP clients over `fetch`), so the memory figures include both.

**What the 20,000 rounds held:**
- 8,942 edits by the person (2,182 additions, 4,703 changes, 2,057 removals);

- 1,595 undos and 103 redos;

Undo and redo that could not apply were also counted, together whatever the reason: 19 undos and 1,063 redos.

## What the soak shows
- **Correctness held.** All 165 reopens gave back exactly the document and revision that were closed.
- **Same seed, same result.** Three 20,000-round runs of seed 230005 gave the same tally, and the same layers, journal and object store at all 40 windows:
  - this one;
  - one before a change that only frees the harness's closed hosts;
  - one before the event stream was added.
- **Edits slow down as the journal grows: #258.**
  - From round 1,000 (82 layers) to round 20,000 (83 layers), the median edit goes from 26 ms to 64 ms, while the journal grows to 25 MiB.
  - Before every append, the store re-reads and hashes the whole journal. That is a deliberate check that nothing else changed it. Hashing 25 MiB takes about 30 ms on this machine, which is nearly all of the growth.
  - The journal is never compacted. It grows about 1.3 KiB per round, and at its 256 MiB limit the project refuses edits.
- **The object store grows with every checkpoint and close: #244.** It reached 24.1 MiB over about 1,390 snapshots, about 18 KiB each.
- **No leaked sockets, servers or referenced timers.**
  - The number of active resources holds at 7 while the session runs.
  - After every host closes, the count is back to what it was before the soak started, compared by kind.
  - The editor's event stream ended with its host at each of the 165 reopens.
  - The count cannot see an unreferenced timer or socket. The event stream's own heartbeat timer is one of those, and is covered only indirectly: it is cleared when its stream ends.
- **No leftover files or folders.**
  - Every temporary file the host writes sits next to its target: in the project, the project folder or the codebase.
  - After closing, the project folder holds only the project's own files and folders: the journal, snapshot, manifest, objects, and the agent and codebase links.
  - The codebase holds only its own file after 989 write-backs.
- **Memory: a slow rise, not attributed.**
  - The heap after a full collection rose from 17.6 MiB (round 1,000) to 27.7 MiB (round 20,000), about 0.5 KiB per round, and keeps rising in a straight line.
  - Two heap snapshots from an earlier run, at rounds 1,000 and 5,000, differ by 1.1 MiB of retained objects. That is less than the 2.6 MiB the heap figure rose over the same span.
  - Among the largest growers are compiled code and its feedback data, and about 170 `WeakRef`s. The product's code creates none, so these most likely come from the driving code's `fetch`.
  - No product data structure is among the largest growers. The rest of the rise is not attributed.
  - Each reopen builds a new host and session, so anything retained across the 165 reopens lives outside them. The longer dogfooding sessions (P08-G11) will show whether it levels off.
  - Resident memory jumped from 149 MiB to 222 MiB by round 1,000 while the process warmed up. It then climbed slowly to 250 MiB by round 16,000, stepped to 289 MiB at round 16,500, and reached 306 MiB at round 19,500.

## Not covered here
- **Child processes.** No action in this soak starts one: the studio host spawns none, and the code that does (agent supervision, the Docling import stack, design assurance) is not reached. The resource count would show a child process left running, but none is started to test it. Child processes are left to P08-G8 (the desktop application's process tree: Electron, its renderer and children) and P08-G11 (dogfooding).
- **Several processes, or several clients, on one project at once:** P08-G6 (concurrency).
- **Sessions longer than 20,000 actions,** and real use: P08-G11 (dogfooding).
