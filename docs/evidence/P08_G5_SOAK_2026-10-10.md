# P08-G5: soak

Issue: #230 (P08 umbrella), founder section P08.5: drift, leaks (memory, handles, child processes, temporary files), journal growth, nondeterminism and degradation.

**Status: measured. One degradation found and filed (#258); the object store's growth (#244) is quantified.**

## What runs
- **`tests/support/soak.mjs`** drives one long session through the studio host. `node tests/support/soak.mjs [rounds] [seed]` prints a JSON report.
- **`tests/soak.test.mjs`** runs 600 rounds on every CI run, twice with the same seed, and checks:
  - latency, the heap after a full collection, and open resources hold steady;
  - after closing, nothing is left running, and only the project's own files are on disk;
  - both runs end in the same document.

  `NINERR_SOAK_ROUNDS` sets the rounds.

**Each round is one action, drawn from the seed:**

| Action | Share |
|---|---:|
| The person's edit: add a layer, change one or remove one | 45% |
| An agent's edit through MCP | 10% |
| Undo | 8% |
| Redo | 6% |
| Reading the document | 10% |
| Exporting a page as code | 5% |
| An HTML import, committed then removed | 4% |
| A write-back to a connected codebase (edit, preview, write) | 5% |
| A checkpoint | 6% |
| Closing and reopening the project in a new host, which must give back the same document and revision | 1% |

**The session stays the same size.** Layers are added and removed in balance, and every import removes the imported pages, since an undo can bring one back. A change in latency is therefore the host's, not a larger document's (#252).

Every 500 rounds the soak records:
- the median of the person's edit latency;
- the heap after a full collection, and the resident memory;
- the journal and object store size on disk;
- the number of the process's active resources (sockets, servers, child processes, timers).

**What the 20,000 rounds held:**
- 8,942 edits by the person (2,182 additions, 4,703 changes, 2,057 removals);
- 2,070 agent edits;
- 1,595 undos and 103 redos;
- 822 imports, 989 write-backs, 1,017 exports and 1,989 reads;
- 1,226 checkpoints and 165 reopens.

## What the soak shows
- **Correctness held.** All 165 reopens gave back exactly the document and revision that were closed.
- **Same seed, same end.** CI's two runs end in the same document. An earlier 20,000-round run of the same seed (before a change that only frees the harness's closed hosts) gave the same tally, journal size and object store size as this one.
- **Edits slow down as the journal grows: #258.**
  - At a steady 83 layers, the median edit goes from 25 ms to 61 ms over 20,000 rounds, while the journal grows to 25 MiB.
  - Before every append, the store re-reads and hashes the whole journal. That is a deliberate check that nothing else changed it. Hashing 25 MiB takes about 30 ms on this machine, which is nearly all of the growth.
  - The journal is never compacted. It grows about 1.3 KB per round, and at its 256 MiB limit the project refuses edits.
- **The object store grows with every checkpoint and close: #244.** It reached 24.1 MiB, while the snapshots it holds are about 18 KB each (24.1 MiB over about 1,390 of them).
- **Nothing is left running.** The number of active resources holds at 5 while the session runs. After every host closes, it is the same as before the soak started.
- **Nothing is left on disk** beyond the project's own files: the journal, snapshot, manifest, objects, and the agent and codebase links. The codebase holds only its own file after 989 write-backs.
- **Memory.**
  - The heap after a full collection rose from 17.3 MiB to 27.2 MiB over 20,000 rounds, about 0.5 KB per round.
  - Two heap snapshots, at rounds 1,000 and 5,000, differ by 1.1 MB of retained objects. Most of that is compiled code and its feedback data, and about 170 `WeakRef`s; the product's code creates none, so these come from Node's own internals. No product data structure grows with the session.
  - This growth is small, and not attributed beyond that. The longer dogfooding sessions (P08-G11) will show whether it levels off.
  - Resident memory rises while the process warms up, then holds between 214 and 303 MiB.
